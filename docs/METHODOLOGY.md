# متدولوژی مرجع توسعه سیستم‌های داشبورد‌محور
نسخه: 1.0

## هدف
تبدیل هر REPO عمومی به یک مشخصات دقیق، قابل‌تأیید و ماشین‌خوان برای توسعه WEB APP داشبوردی؛ با استفاده از LLM به‌عنوان همکار معماری و تولیدکننده، نه تصمیم‌گیر خودمختار.

## قواعد قطعی
1. ابتدا REPO ورودی و ساختار موجود آن بررسی می‌شود؛ سپس سؤال می‌پرسیم.
2. از اطلاعات موجود در کد، فایل‌ها، نمونه داده‌ها و پاسخ صریح مالک استفاده کن؛ حدس را واقعیت تلقی نکن.
3. وضعیت هر داده/تصمیم: OBSERVED، OWNER_PROVIDED، PROPOSED، ASSUMPTION، UNKNOWN، APPROVED، REJECTED، BLOCKED، IMPLEMENTED یا VERIFIED.
4. پرسش‌ها مرحله‌ای و فقط درباره خلأهای واقعی باشند؛ از پرسشنامه طولانی یک‌باره پرهیز شود.
5. ساختار و قراردادهای موجود REPO مقصد حفظ شود؛ فایل‌های مشابه و متناقض نساز.
6. ثابت یا قابل‌تنظیم بودن هدر، فوتر، منو، صفحات و ویجت‌ها باید صریح باشد. کنترل افزودن/حذف/جابجایی برای ادمین ایجاد نکن مگر تأیید شده باشد.
7. UI، داده، منبع، KPI، تعامل، ترجمه، امنیت و معیار پذیرش را جدا تعریف کن.
8. هیچ فایل موجودی بدون تأیید صریح بازنویسی نشود.
9. Token، رمز، credential و داده حساس در REPO ثبت نشود.
10. فقط کاری را Push یا تست‌شده اعلام کن که واقعاً انجام شده است. IMPLEMENTED به‌معنی VERIFIED نیست.

## مراحل کشف و تعریف
A. بررسی REPO: شاخه پیش‌فرض، درخت فایل‌ها، README، فناوری موجود، مشخصات، تصاویر مرجع، assets، نمونه داده، تست‌ها و CI. محتوای غیرقابل‌خواندن «بررسی‌نشده» است، نه اینکه وجود ندارد.

B. شناسنامه محصول: نام، هدف، نقش‌ها، تصمیم‌هایی که داشبورد پشتیبانی می‌کند، معیار موفقیت، محیط استقرار، محدودیت‌ها و موارد خارج از محدوده.

C. پوسته برنامه: عنوان، لوگو و مسیر واقعی آن، هدر، فوتر، تصویر پس‌زمینه، سایدبار، زبان‌ها، RTL/LTR، فونت، تم، واکنش‌گرایی، دسترس‌پذیری، خطا و بارگذاری.

D. صفحات: شناسه یکتا، عنوان، مسیر، هدف، ترتیب منو، چیدمان ردیف/ستون، اندازه واکنش‌گرا، فیلترها و عملیات.

E. ویجت: شناسه، صفحه والد، هدف، نوع بصری، موقعیت/ابعاد، فیلدها، قالب نمایش، فیلتر، مرتب‌سازی، تجمیع، واحد، تعامل، Drill-down، وضعیت‌های داده و معیار پذیرش.

F. قرارداد داده: نوع منبع (فایل/API/سرویس/DB/mock)، نام/مسیر/endpoint، LIVE یا DEMO، ساختار نمونه، نام و نوع فیلدها، واحد، زمان داده، تازگی، صفحه‌بندی، خطا، سطح دسترسی. آدرس و پارامتر اتصال را حدس نزن.

G. KPI و هشدار: تعریف، فرمول، دامنه، واحد، بازه زمانی، رفتار داده خالی/ناقص/قدیمی، منبع آستانه، شدت هشدار و مثال اعتبارسنجی. آستانه عملیاتی بدون تأیید مالک ساخته نشود.

H. حالت‌ها: DISPLAY، MONITOR/ALERT و EXECUTE/ACTION. پیش‌فرض READ-ONLY است. اجرای عملیات نیازمند مجوز، تأیید کاربر، audit، مدیریت خطا و rollback مشخص است.

I. آزمون پذیرش: انطباق قرارداد داده، ارجاع‌ها، زبان‌ها، RTL/LTR، واکنش‌گرایی، دسترسی، امنیت و رفتار خطا. نتیجه تستی که اجرا نشده NOT_RUN است.

## قرارداد هر ویجت
حداقل فیلدها: id، page_id، purpose، status، placement، visual_type، source_ref، data_contract_ref، fields، metric_refs، interactions، states، localization_keys، acceptance_criteria، evidence_refs و decision_refs.

## وضعیت داده
loading، success، empty، partial، stale، unavailable، unauthorized و error را بررسی کن. داده گمشده نباید بی‌صدا به صفر، false یا وضعیت سالم تبدیل شود.

## حلقه همکاری LLM
بررسی → گزارش شواهد و خلأها → پرسش کوتاه بعدی → ثبت پاسخ و منشأ → ارائه تغییر پیشنهادی → تأیید در موارد لازم → ثبت مشخصات → اعتبارسنجی → Push با مجوز → گزارش فایل‌ها، commit، تست‌ها و موارد باز.

## معیار تکمیل مرحله مشخصات
تمام صفحات و ویجت‌ها شناسه و جایگاه روشن داشته باشند؛ هر ویجت داده‌محور قرارداد منبع معتبر یا BLOCKER داشته باشد؛ تعریف KPIها تأیید شده یا صریحاً باز بماند؛ حالت‌های داده، زبان‌ها و معیار پذیرش مشخص باشند. این معیار به‌معنی پیاده‌سازی خود برنامه نیست.
